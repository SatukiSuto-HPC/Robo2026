# Debug Report: MakerLine Arm Integration (MicroPython)

## 概要
ESP32用MicroPythonプロジェクトのデバッグ分析を行いました。ビルドは行わず、コード静的解析とメモリ使用量の推定に基づいて問題点を報告します。

## 1. メモリ使用量（RAM/Flash）

### 1.1 ファイルサイズ
| ファイル | 行数 | サイズ（バイト） |
|----------|------|------------------|
| arm.py | 165 | 7,603 |
| boot.py | 42 | 1,726 |
| config.py | 53 | 1,979 |
| kinematics.py | 91 | 3,910 |
| line_follower.py | 211 | 9,447 |
| main.py | 48 | 1,788 |
| teaching.py | 153 | 5,849 |
| web_server.py | 151 | 7,128 |
| **合計** | **914** | **39,430** |

### 1.2 推定RAM使用量
- MicroPythonインタプリタオーバーヘッド：約100-200KB
- 各モジュールのクラス/関数オブジェクト：約50-100KB
- 実行時データ構造（PWM、Pin、UARTなど）：約20-50KB
- **総計：約200-400KB**（ESP32の2MB RAM内で余裕あり）

### 1.3 フラッシュメモリ使用量
- ファイルシステム（FFat/LittleFS）：約50-100KB
- `index.html`（ストリーミング用）：約7KB
- `teaching.json`（動的生成）：最大数KB
- **総計：約100-150KB**（4MB Flash内で余裕あり）

## 2. 問題点

### 2.1 メモリ関連
- **[軽微]** `web_server.py`の`_stream_buf`（512バイト）は再利用可能だが、大きなファイル送信時はメモリ断片化の可能性。
- **[軽微]** `gc.collect()`が各HTTPリクエスト後に呼び出される（`web_server.py:172`）。頻繁なGCはパフォーマンスに影響する可能性。

### 2.2 フラッシュメモリ関連
- **[要注意]** `teaching.py`の`save_to_json()`は頻繁な書き込みを行う。フラッシュ書き込み回数制限（通常10万回）に接近する可能性。
- **[提案]** 書き込み頻度を下げ、変更があった時のみ保存するか、バッファリングを検討。
- **[軽微]** `index.html`はフラッシュからストリーミングされるが、メモリ制約が厳しい環境では問題なし。

### 2.3 コードの重複・非効率
- **[中程度]** `line_follower.py`の`execute_turn_left_step()`と`step_motors()`でモーター制御コードが重複。
- **[軽微]** `arm.py`と`teaching.py`で関節角の取得方法が異なる（`getCurrentTheta1` vs `_current_theta1`）。
- **[軽微]** `config.py`の定数とハードコードされた定数（`MAX_TEACH_POINTS`など）が混在。

### 2.4 エラー処理
- **[中程度]** `web_server.py`のリクエスト解析が簡易的。 malformedリクエストに対する耐性不足。
- **[軽微]** 多くの例外が`except Exception: pass`で無視されている。デバッグ困難な場合あり。
- **[軽微]** `arm.py`の`detach_servos()`でGPIOピンをLOWに設定する処理が冗長。

### 2.5 パフォーマンス
- **[軽微]** `main.py`の`time.sleep_us(500)`は約500Hzの更新頻度。センサー読み取り（~1kHz）とのバランス考慮必要。
- **[軽微]** `kinematics.py`の三角関数（`math.radians`、`math.cos`など）はCPU負荷较高い。リアルタイム性が必要な場面での影響。

### 2.6 セキュリティ
- **[要注意]** Wi-Fi APがオープンネットワーク（パスワードなし）。公共の場での使用は危険。
- **[要注意]** HTTPは暗号化されていない。通信の傍受・改ざんが可能。
- **[提案]** ローカルネットワーク限定の使用を想定し、セキュリティ文書を追加。

### 2.7 ハードウェア依存
- **[要注意]** ピン設定（`config.py`）はESP32-WROOM-32Eを想定。ESP32-S3など他モデルではピン配置が異なる可能性。
- **[要注意]** UART2（GPIO 21/22）はESP32モデルによって異なるUARTである場合あり。
- **[提案]** 複数モデル対応の検討またはドキュメント追加。

### 2.8 論理的な問題
- **[中程度]** `teaching.py`の`record_current()`はプライベート変数`_current_theta1`に直接アクセス（カプセル化違反）。
- **[中程度]** `line_follower.py`の`check_all_line_condition()`はデバウンス処理が複雑。状態管理の見直しが必要。
- **[軽微]** `web_server.py`の`/api/status`エンドポイントがプライベート変数`_is_attached`を直接参照。

### 2.9 コード品質
- **[軽微]** コメントが英語と日本語混在。一貫性欠如。
- **[軽微]** 定数（`MAX_TEACH_POINTS`など）がファイル内にハードコード。`config.py`への移動が望ましい。
- **[軽微]** エラーメッセージが日本語と英語混在（例：`"[ARM ERROR] Failed to attach servos: {e}"`）。

## 3. ESP32固有の注意点

### 3.1 起動時
- `boot.py`で`gc.collect()`を呼び出し、メモリ断片化を軽減している。これは有効。
- Wi-Fi AP起動に約1秒程度かかる可能性がある。`time.sleep(0.2)`は適切。

### 3.2 パフォーマンス
- `uselect.poll()`はESP32のMicroPythonでサポートされており、非ブロッキングI/Oに適している。
- PWM周波数50Hzはサーボ制御に適し、16ビット解像度は十分。

### 3.3 フラッシュ書き込み
- `teaching.json`の頻繁な書き込みはフラッシュ劣化を促進。書き込み回数を制限する対策が必要。

## 4. 推奨される改善点（優先度順）

### 高優先度
1. `teaching.json`の書き込み頻度を削減（変更時のみ保存、またはバッファリング）。
2. Wi-Fi APにパスワードを設定するか、セキュリティ文書を追加。
3. `line_follower.py`のモーター制御コードを統合し、重複を除去。

### 中優先度
4. `web_server.py`のリクエスト解析を強化し、malformedリクエストへの耐性を向上。
5. `teaching.py`のプライベート変数直接アクセスを公開メソッド経由に変更。
6. `config.py`にすべての定数を集約し、ハードコードを除去。

### 低優先度
7. コメントとエラーメッセージの一貫性を向上（言語統一）。
8. メインループの更新頻度（500Hz）とセンサー読み取り頻度のバランスを再評価。
9. 複数ESP32モデル対応の検討またはドキュメント追加。

## 5. 結論
プロジェクトは全体的に良好な構造を持ち、ESP32のメモリ制約内でおおむね動作可能である。ただし、フラッシュ書き込み頻度とセキュリティ面での改善が必要。優先度の高そうな問題から順に対応することを推奨する。
